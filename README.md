# VOLNA — React, FastAPI, PostgreSQL и Kubernetes

**Основной сайт проекта: http://localhost:8088.** Здесь используются существующие аккаунты и игроки из Kubernetes. Для обычного запуска и обновления используй `scripts/start-k8s.ps1`; Compose отдельно запускать не требуется.

Учебный сайт волейбольной команды с двумя самостоятельными API. Регистрация, сессии, профиль и аватарки принадлежат `accounts`. Сведения о команде, игроки и их фотографии принадлежат `team-info`. У каждого API своя база PostgreSQL. `team-info` проверяет сессию HTTP-запросом в `accounts` и не читает его таблицы.

## Компоненты

| Компонент | Назначение |
|---|---|
| frontend | React/Vite, раздача сайта и API-шлюз Nginx |
| accounts | Регистрация, вход, сессии, профиль и аватарки |
| accounts-db | PostgreSQL: users и user_sessions |
| team-info | Сведения о команде, игроки, фотографии |
| team-info-db | PostgreSQL: team и players |
| pgadmin | Администрирование обеих баз |

Выбор любимой команды меняет палитру сайта. Для шести команд предусмотрены светлая и тёмная темы. Состав отображается каруселью минимум из 12 мест. Пустые места не создают фиктивных записей в базе. Зарегистрированные пользователи могут добавлять и удалять игроков; отдельной роли администратора нет.

В форме добавления и в раскрытой карточке доступно поле «Об игроке» (до 2000 символов). Вошедший пользователь может сохранить или изменить текст, посетители видят сохранённое описание с абзацами. Описание хранится в PostgreSQL; при обновлении существующей базы столбец добавляется автоматически без удаления игроков.

## Быстрый запуск в Kubernetes

Рабочий стенд использует Docker Desktop, контекст `docker-desktop` и namespace `default`. После подключения Argo CD версии приложений задаются веткой `deploy`, которую обновляет CI. Для обычного открытия уже развёрнутого сайта из корня проекта выполни:

```powershell
.\scripts\start-k8s.ps1 -PortForwardOnly
```

Оставь терминал открытым. Сайт: http://localhost:8088; pgAdmin: http://localhost:8085. С параметром `-ApiPorts` документация API доступна на http://localhost:8002/docs и http://localhost:8003/docs. После замены Pod скрипт восстанавливает пробросы автоматически. Ctrl+C завершает пробросы, приложения и диски остаются в кластере.

Изменения приложения отправляй в ветку `dev`. После успешных тестов и публикации образов CI обновит ветку `deploy`; Argo CD применит новую сборку. Вручную пересобирать и импортировать образы на компьютер не требуется.

На новом компьютере сначала включи Kubernetes, настрой доступ к GHCR по следующему разделу и выполни `scripts/install-argocd.ps1`. Для PVC нужен StorageClass по умолчанию. Само наличие GitHub-репозитория не переносит базы и фотографии с другого компьютера.

Локальная сборка через `scripts/start-k8s.ps1` и ручной режим `-UseGhcr` сохранены для стенда без Application Argo CD `volna`. Если она уже создана, скрипт останавливает ручное применение манифестов и предлагает `-PortForwardOnly`, чтобы два механизма не перезаписывали настройки друг друга.

## Запуск опубликованной сборки из GHCR

После успешного CI три проверенных образа публикуются в GitHub Container Registry: `ghcr.io/g4stt/volleyball-team-accounts`, `ghcr.io/g4stt/volleyball-team-team-info` и `ghcr.io/g4stt/volleyball-team-frontend`. У каждого есть тег ветки (`dev` или `main`) и тег `sha-<полный SHA коммита>`.

Для воспроизводимого запуска скрипт принимает именно тег `sha-…`: так все три приложения используют одну выбранную опубликованную сборку. В режиме GHCR нужны Docker Desktop с готовым Kubernetes и `kubectl`; Python, Kaniko и импортёр локальных образов не запускаются.

### Доступ к приватным образам: один раз

1. Запусти Docker Desktop и дождись готовности Kubernetes.
2. В GitHub открой **Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token (classic)**. Выбери срок действия и только разрешение **read:packages**. Токен должен принадлежать пользователю с доступом к этим пакетам.
3. Из корня проекта запусти:

```powershell
.\scripts\set-ghcr-secret.ps1
```

Вставь токен в скрытый запрос ввода и нажми Enter. Скрипт передаёт данные через stdin в Kubernetes Secret `ghcr-credentials` типа `kubernetes.io/dockerconfigjson` в namespace `default`. Он не записывает токен в файл проекта, аргументы командной строки или Git. Для другого пользователя передай `-Username имя`. При истечении токена выпусти новый и повтори команду.

### Запуск выбранной версии

Возьми полный SHA коммита из успешного запуска CI, в котором завершился шаг **Publish tested Docker images**. Например, первая опубликованная сборка запускается так:

```powershell
.\scripts\start-k8s.ps1 -UseGhcr -ImageTag sha-ca56bebc8a1e9080a428df82adfddc35bc7563c1
```

Скрипт подставляет адреса GHCR и ссылку на `ghcr-credentials` в шаблоны Pod трёх Deployment, применяет манифесты и ожидает готовности. Имена PostgreSQL, Secret баз, PVC и каталогов изображений сохраняются. Сайт открывается по прежнему адресу http://localhost:8088. Перед повторным запуском заверши предыдущие пробросы портов через Ctrl+C в терминале запуска.

Для обновления отправь код в GitHub, дождись успешной публикации и запусти эту же команду с новым `sha-…`. Это ручной режим для стенда без Argo CD. В автоматическом режиме используется отдельная ветка deploy, как описано ниже.

Сгенерированные манифесты находятся в `.run/manifests-ghcr` и исключены из Git. Проверить их без подключения к кластеру и применения можно так:

```powershell
.\scripts\start-k8s.ps1 -UseGhcr -ImageTag sha-ca56bebc8a1e9080a428df82adfddc35bc7563c1 -RenderOnly
```

Если все три пакета уже публичные, запуск без Secret доступен с дополнительным параметром `-ImagePullSecret ''`. Скрипт не меняет видимость пакетов на GitHub. Исходные `K8s/*.yaml` остаются шаблонами для локальной сборки; для запуска из реестра используй `-UseGhcr`, чтобы адреса и доступ были подставлены согласованно.

При `ImagePullBackOff` проверь срок токена, разрешение `read:packages` и наличие выбранного SHA-тега у всех трёх пакетов. Посмотреть причину можно через `kubectl --context docker-desktop -n default describe pod имя-pod`. Остановка пробросов по-прежнему выполняется `scripts/stop-k8s.ps1`.

## Автоматическое развёртывание через Argo CD

Поток обновления: **push в dev → проверки Python и React → сборка и интеграционные тесты → публикация образов в GHCR → продвижение манифестов в deploy → синхронизация Argo CD**.

- `K8s/kustomization.yaml` объединяет прежние четыре файла ресурсов.
- `deploy/desktop/kustomization.yaml` подставляет GHCR-образы с SHA-тегом и `imagePullSecrets: ghcr-credentials` для трёх приложений. Имена баз, Service и PVC сохранены.
- `deploy/argocd/project.yaml` ограничивает приложение одним репозиторием, namespace `default` и необходимыми типами ресурсов.
- `deploy/argocd/application.yaml` описывает Application `volna`: ветка `deploy`, каталог `manifests`, автоматическая синхронизация и self-heal.
- `scripts/install-argocd.ps1` устанавливает фиксированную версию Argo CD **v3.5.7** в namespace `argocd`, затем создаёт проект и приложение. Установка рассчитана на собственный локальный учебный кластер. Официальный Redis используется через Docker Hub; фиксированные образы могут использовать кеш узла.

Задание **Promote tested release to Argo CD** работает только после успешного CI при push в `dev`. Оно генерирует манифесты из проверенного коммита и подставляет один и тот же опубликованный SHA-тег для всех трёх образов. Ветка `deploy` создаётся автоматически при первом запуске и содержит `manifests/volna.yaml` и `manifests/source-revision.txt`. Если в `dev` уже есть более новый коммит, устаревший запуск не продвигает свою сборку. Force push не используется. Заданию выдано `contents: write`; право записи в репозиторий должно быть разрешено настройками GitHub Actions и правилами ветки `deploy`.

Argo CD не следит за исходной веткой `dev`: изменения становятся желаемой конфигурацией кластера после продвижения в `deploy`. GitHub не получает kubeconfig, токен GHCR на чтение или пароль Argo CD. Argo CD читает публичный Git-репозиторий, а узел Kubernetes скачивает приватные образы через существующий Secret.

Для установки или повторного применения настройки:

```powershell
.\scripts\install-argocd.ps1
```

После первого push нового workflow дождись задания **Promote tested release to Argo CD**. До создания ветки `deploy` Application может показывать ошибку чтения исходников; после появления ветки она должна перейти в `Synced` и `Healthy`. Проверка:

```powershell
kubectl --context docker-desktop -n argocd get application volna
kubectl --context docker-desktop -n default get pods
```

Чтобы запросить немедленную повторную проверку Git вместо ожидания очередного опроса:

```powershell
kubectl --context docker-desktop -n argocd annotate application volna argocd.argoproj.io/refresh=hard --overwrite
```

В отдельном терминале можно открыть интерфейс Argo CD:

```powershell
kubectl --context docker-desktop -n argocd port-forward service/argocd-server 8090:443 --address=127.0.0.1
```

Адрес: https://localhost:8090; логин: `admin`. Argo CD использует собственный сертификат. Начальный пароль можно получить только в своём терминале:

```powershell
$encodedPassword = kubectl --context docker-desktop -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}'
[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($encodedPassword))
```

После первого входа смени пароль в интерфейсе. Если он уже изменён, используй новый пароль, а не значение начального Secret.

Автоматическое удаление ресурсов (`prune`) выключено. Для явно описанных PVC дополнительно заданы `Prune=false,Delete=false`; у Application нет finalizer каскадного удаления. Диски StatefulSet остаются существующими. Это не заменяет резервное копирование базы. Прямые ручные изменения управляемых ресурсов Argo CD возвращает к состоянию из Git.

## Что делает сборка

В отдельном namespace `volleyball-build` работает локальный учебный registry. Источники для сборки передаются во временные Pod без `.env`, `.venv`, `node_modules` и `dist`. Сборка не требует Docker-сокета. Временный импортёр использует сокет containerd и установленный на узле `ctr`, поэтому этот режим предназначен только для собственного локального Docker Desktop, а не для общего или производственного кластера. После успешной работы временные Pod и их ConfigMap удаляются; registry и его кеш сохраняются.

Для Docker Desktop предусмотрен прямой импорт образов в containerd: на проверенном стенде скачивание образов через HTTP NodePort возвращало `unexpected EOF`. Импортёр не меняет конфигурацию containerd и не удаляет образы. На многоузловом или удалённом кластере вместо этого нужен доступный всем узлам реестр с нормальной настройкой TLS и доступа.

Каждая сборка получает отдельный тег. Подставленные манифесты и журналы локального запуска находятся в `.run`, исключённой из Git. Исходные файлы `K8s/*.yaml` содержат тег `k8s-v1` как базовый пример; для обычного запуска используй скрипт, который подставляет тег текущей сборки.

## Манифесты

- `K8s/accounts.yaml`: Accounts API, PostgreSQL, сетевые объекты, Secret и хранилища.
- `K8s/team-info.yaml`: Team Info API, отдельный PostgreSQL, Secret и хранилища.
- `K8s/frontend.yaml`: сайт и сетевой доступ.
- `K8s/pgadmin.yaml`: pgAdmin, преднастроенные подключения к базам и хранилище его настроек.

Для API используются `/health` (работа HTTP-приложения) и `/ready` (включая проверку соединения с собственной БД). Запуск API ожидает PostgreSQL через initContainer. В обоих API создание схемы защищено транзакционной advisory-блокировкой.

На первом этапе запускается одна реплика каждого API. Стратегия Recreate упрощает использование локальных RWO-дисков фотографий. Для распределения реплик по нескольким узлам потребуется общее хранилище изображений, отдельная настройка обновлений и общий механизм ограничения попыток входа. StatefulSet сам не настраивает репликацию PostgreSQL.

## Локальные учётные данные

Значения ниже демонстрационные и явно записаны в Secret-манифестах для локальной практики.

| Назначение | Пользователь | Пароль |
|---|---|---|
| PostgreSQL accounts | accounts_user | test_password |
| PostgreSQL team_info | team_info_user | team_info_lab_password |
| Вход в pgAdmin | admin@example.com | pgadmin_lab_password |

Приложение не создаёт готового пользователя сайта: зарегистрируйся через форму. В pgAdmin автоматически добавлены серверы Accounts PostgreSQL и Team Info PostgreSQL; при первом соединении введи пароль соответствующей базы. Вход в pgAdmin и вход в PostgreSQL — разные учётные записи.

Изменение Secret с паролем уже инициализированного PostgreSQL не меняет пароль существующей роли: его нужно менять SQL-командой и затем согласовать настройки приложения. Не удаляй PVC ради смены пароля.

## Проверки

```powershell
kubectl get pods,svc,pvc
python .\scripts\smoke-test.py
```

Smoke-проверка идёт через Nginx сайта: регистрация, дубликат логина, неправильный пароль, сессия, все шесть предпочтений команды, аватарка, проверка авторизации между API, создание игрока с фото, дубликат номера, удаление игрока и выход. Создаётся отдельный тестовый аккаунт с префиксом `check_`; тестовый игрок удаляется.

Для ручной проверки Swagger в изменяющих запросах передавай заголовок `x-requested-with` со значением `VolnaApp`. Через сайт он передаётся автоматически. Cookie относится к имени хоста: во время проверки не переключайся между `localhost`, `127.0.0.1` и `0.0.0.0`.

Проверка сохранности данных после замены Pod:

```powershell
python .\scripts\smoke-test.py --keep-state
kubectl rollout restart deployment/accounts deployment/team-info
kubectl delete pod accounts-db-0 team-info-db-0
kubectl rollout status statefulset/accounts-db
kubectl rollout status statefulset/team-info-db
kubectl rollout status deployment/accounts
kubectl rollout status deployment/team-info
python .\scripts\smoke-test.py --verify-persistence
```

Этот сценарий создаёт собственные тестовые записи и проверяет сохранение пользователя, сессии, предпочтения команды, аватарки, игрока и его фото. Он не удаляет PVC и не затрагивает чужие записи.

## Остановка и повторный запуск

```powershell
.\scripts\stop-k8s.ps1
```

Команда завершает только пробросы портов, созданные скриптом проекта. Приложения продолжают работать в кластере. Чтобы временно остановить их, сохранив диски:

```powershell
kubectl scale deployment accounts team-info frontend pgadmin --replicas=0
kubectl scale statefulset accounts-db team-info-db --replicas=0
```

Для возврата к работе выполни `start-k8s.ps1 -SkipBuild`. Не удаляй PVC и не сбрасывай кластер, если нужны данные.

## Данные и переход с Compose

Существующие PVC аккаунтов сохраняются. У Team Info новая отдельная база: начальные сведения о команде создаются автоматически, игроки добавляются через сайт. Старые записи PostgreSQL/MySQL и файлы из Docker-томов не копируются в Kubernetes автоматически. Старый каталог `backend`, SQL и прежние тома оставлены для возможного переноса данных.

`compose.yaml` сохранён для отдельной практики с Docker Compose. Все его сервисы находятся в профиле `compose-lab` и по умолчанию не запускаются. Существующие контейнеры Compose остановлены, их тома сохранены. Основной рабочий сайт использует Kubernetes.

Раньше параллельно работали две копии: Compose с пустым составом и Kubernetes с сохранёнными игроками. Это разные базы, поэтому записи из одной копии не появлялись в другой. Для обычной работы теперь используется только http://localhost:8088. В Compose также указан порт 8088: он не позволит незаметно поднять второй сайт рядом с основным. Включение учебного профиля не переносит в него данные Kubernetes.

Изменения сайта собирай через `scripts/start-k8s.ps1`, как указано выше. Сборка через `docker compose build` сама по себе не обновляет приложения в Kubernetes. `.env.example` остаётся примером настроек Compose; фактический `.env` не изменён.

`healthcheck.test` — команда проверки внутри контейнера. Для API она запускает контейнерный Python и делает запрос к `/ready`, который проверяет также подключение к PostgreSQL. `urllib.request` — встроенный модуль Python; устанавливать его через pip или на компьютер ради этой проверки не нужно. `404` означает, что в запущенной версии приложения нет такого маршрута: проверь исходник и пересобери образ. Фронтенд проверяется встроенной в Alpine командой `wget` по `/healthz`.

## Автоматические проверки в GitHub Actions (CI)

Workflow `.github/workflows/ci.yml` запускается при push в `dev` и `main`, а также для pull request в эти ветки. После загрузки файла ход выполнения виден во вкладке **Actions → CI**. Новая отправка в ту же ветку отменяет её предыдущую незавершённую проверку.

Проверки выполняются на временных Ubuntu-машинах GitHub:

1. **Python / accounts** и **Python / team_info** — установка зависимостей для Python 3.12, `pip check`, компиляция модулей, проверка импорта приложения и генерации OpenAPI.
2. **React build** — Node.js 22, установка по `package-lock.json` через `npm ci` и сборка Vite.
3. **Docker builds and integration** — сборка трёх Docker-образов, запуск двух PostgreSQL и приложений, smoke-тест через Nginx, пересоздание контейнеров и проверка сохранности данных. Этот этап начинается после успешных проверок Python и React.

Файл `.github/compose.ci.yaml` описывает только временный стенд CI. Он создаёт собственные базы и тома с префиксом проекта `volna-ci`, использует тестовые пароли и публикует сайт на `127.0.0.1:18088`. Рабочий стенд по-прежнему запускается в Kubernetes. Секреты репозитория и доступ к локальному кластеру для CI не нужны.

В конце запуска в журнал выводятся состояние контейнеров и логи, после чего контейнеры, сеть и тестовые тома удаляются даже при ошибке. После успешных тестов при push workflow входит в GHCR через встроенный GITHUB_TOKEN и публикует те же проверенные образы с тегом ветки и SHA коммита. Разрешение packages: write выдано только заданию integration. При pull request публикация пропускается. Задание gitops после публикации продвигает манифесты в ветку deploy, за которой следит Argo CD. Публикация образов в main сохранена; автоматическое продвижение стенда выполняется только из dev.

Для ручного повторного запуска уже опубликованного workflow открой **Actions → CI → Run workflow** и выбери ветку `dev`. ## Библиотеки Python

- `pydantic` — проверка и преобразование входных данных.
- `Pillow` — проверка и обработка фотографий и аватарок; импортируется как `PIL`.
- `fastapi` — фреймворк маршрутов и обработчиков HTTP API.
- `uvicorn` — сервер, запускающий приложение FastAPI.
- `psycopg[binary]` — драйвер PostgreSQL с готовыми двоичными компонентами.
- `python-multipart` — разбор HTML-форм и загружаемых файлов.
- `httpx` — HTTP-клиент сервиса Team Info для проверки сессий через Accounts API.

Версии зависимостей закреплены в `requirements.txt` каждого API. Встроенные модули `os`, `contextlib`, `pathlib` и другие отдельно не устанавливаются.

## Файл pyproject.toml

`pyproject.toml` — текстовая конфигурация Python-проекта в формате TOML. В разделе `[project]` указаны название `volleyball-team`, версия `0.1.0` и требование Python `>=3.12`. Версия проекта не обязана совпадать с версией API. Пустой список `dependencies` не означает отсутствия библиотек: для контейнеров они устанавливаются из отдельных `requirements.txt`.

Вызов `FastAPI(...)` создаёт объект приложения в памяти и не создаёт `pyproject.toml`. Настройки инструментов разработки при необходимости располагают в разделах `[tool.*]`. Python 3.12 в Dockerfile соответствует заявленному минимальному требованию проекта.
