# VOLNA — React, FastAPI, PostgreSQL и Kubernetes

**Основной сайт проекта: http://localhost:8088.** Здесь используются существующие аккаунты и игроки из Kubernetes. Для обычного запуска и обновления используй `scripts/start-k8s.ps1`; Compose отдельно запускать не требуется.

Учебный сайт волейбольной команды с двумя самостоятельными API. Регистрация, сессии, профиль и аватарки принадлежат `accounts`. Сведения о команде, игроки и их фотографии принадлежат `team-info`. У каждого API своя база PostgreSQL. `team-info` проверяет сессию HTTP-запросом в `accounts` и не читает его таблицы.

## Компоненты

| Компонент | Назначение |
|---|---|
| frontend | React/Vite, раздача сайта и API-шлюз Nginx |
| accounts | Регистрация, вход, сессии, профиль и аватарки |
| accounts-db | PostgreSQL: users и user_sessions |
| team-info | Сведения о команде, игроки, фотографии |
| team-info-db | PostgreSQL: team и players |
| pgadmin | Администрирование обеих баз |

Выбор любимой команды меняет палитру сайта. Для шести команд предусмотрены светлая и тёмная темы. Состав отображается каруселью минимум из 12 мест. Пустые места не создают фиктивных записей в базе. Зарегистрированные пользователи могут добавлять и удалять игроков; отдельной роли администратора нет.

В форме добавления и в раскрытой карточке доступно поле «Об игроке» (до 2000 символов). Вошедший пользователь может сохранить или изменить текст, посетители видят сохранённое описание с абзацами. Описание хранится в PostgreSQL; при обновлении существующей базы столбец добавляется автоматически без удаления игроков.

## Быстрый запуск в Kubernetes

Нужны Docker Desktop с работающим **одноузловым** кластером, контекст `docker-desktop`, `kubectl`, Python 3.12 или новее и `tar`. В кластере должен быть StorageClass по умолчанию. Скрипт рассчитан на локальный учебный кластер с административным доступом.

Из корня проекта в PowerShell:

```powershell
.\scripts\start-k8s.ps1
```

Если Windows запрещает запуск локального скрипта, разрешить его только для этого процесса можно так:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start-k8s.ps1
```

Скрипт собирает три образа из Dockerfile **внутри кластера** с Kaniko, загружает их в containerd локального узла, применяет четыре манифеста, ожидает готовности приложений и создаёт локальные пробросы портов. Оставь терминал открытым; Ctrl+C завершит пробросы, но не остановит приложения в кластере.

| Что открыть | Адрес |
|---|---|
| Сайт | http://localhost:8088 |
| Профиль | http://localhost:8088/#account |
| pgAdmin | http://localhost:8085 |

Повторный запуск без пересборки уже подготовленных образов:

```powershell
.\scripts\start-k8s.ps1 -SkipBuild
```

После изменения текста, стилей или кода приложения закрой предыдущий терминал запуска через Ctrl+C и выполни `scripts/start-k8s.ps1` без `-SkipBuild`. Скрипт пересоберёт образы и обновит приложения, сохранив существующие базы и изображения. Открывай тот же адрес http://localhost:8088; при необходимости обнови страницу через Ctrl+F5.

Для прямого доступа к Swagger добавь `-ApiPorts`. Документация аккаунтов откроется на http://localhost:8002/docs, команды — на http://localhost:8003/docs. При занятых портах сайта и pgAdmin можно передать `-SitePort 8090 -PgAdminPort 8091`.

## Что делает сборка

В отдельном namespace `volleyball-build` работает локальный учебный registry. Источники для сборки передаются во временные Pod без `.env`, `.venv`, `node_modules` и `dist`. Сборка не требует Docker-сокета. Временный импортёр использует сокет containerd и установленный на узле `ctr`, поэтому этот режим предназначен только для собственного локального Docker Desktop, а не для общего или производственного кластера. После успешной работы временные Pod и их ConfigMap удаляются; registry и его кеш сохраняются.

Для Docker Desktop предусмотрен прямой импорт образов в containerd: на проверенном стенде скачивание образов через HTTP NodePort возвращало `unexpected EOF`. Импортёр не меняет конфигурацию containerd и не удаляет образы. На многоузловом или удалённом кластере вместо этого нужен доступный всем узлам реестр с нормальной настройкой TLS и доступа.

Каждая сборка получает отдельный тег. Подставленные манифесты и журналы локального запуска находятся в `.run`, исключённой из Git. Исходные файлы `K8s/*.yaml` содержат тег `k8s-v1` как базовый пример; для обычного запуска используй скрипт, который подставляет тег текущей сборки.

## Манифесты

- `K8s/accounts.yaml`: Accounts API, PostgreSQL, сетевые объекты, Secret и хранилища.
- `K8s/team-info.yaml`: Team Info API, отдельный PostgreSQL, Secret и хранилища.
- `K8s/frontend.yaml`: сайт и сетевой доступ.
- `K8s/pgadmin.yaml`: pgAdmin, преднастроенные подключения к базам и хранилище его настроек.

Для API используются `/health` (работа HTTP-приложения) и `/ready` (включая проверку соединения с собственной БД). Запуск API ожидает PostgreSQL через initContainer. В обоих API создание схемы защищено транзакционной advisory-блокировкой.

На первом этапе запускается одна реплика каждого API. Стратегия Recreate упрощает использование локальных RWO-дисков фотографий. Для распределения реплик по нескольким узлам потребуется общее хранилище изображений, отдельная настройка обновлений и общий механизм ограничения попыток входа. StatefulSet сам не настраивает репликацию PostgreSQL.

## Локальные учётные данные

Значения ниже демонстрационные и явно записаны в Secret-манифестах для локальной практики.

| Назначение | Пользователь | Пароль |
|---|---|---|
| PostgreSQL accounts | accounts_user | test_password |
| PostgreSQL team_info | team_info_user | team_info_lab_password |
| Вход в pgAdmin | admin@example.com | pgadmin_lab_password |

Приложение не создаёт готового пользователя сайта: зарегистрируйся через форму. В pgAdmin автоматически добавлены серверы Accounts PostgreSQL и Team Info PostgreSQL; при первом соединении введи пароль соответствующей базы. Вход в pgAdmin и вход в PostgreSQL — разные учётные записи.

Изменение Secret с паролем уже инициализированного PostgreSQL не меняет пароль существующей роли: его нужно менять SQL-командой и затем согласовать настройки приложения. Не удаляй PVC ради смены пароля.

## Проверки

```powershell
kubectl get pods,svc,pvc
python .\scripts\smoke-test.py
```

Smoke-проверка идёт через Nginx сайта: регистрация, дубликат логина, неправильный пароль, сессия, все шесть предпочтений команды, аватарка, проверка авторизации между API, создание игрока с фото, дубликат номера, удаление игрока и выход. Создаётся отдельный тестовый аккаунт с префиксом `check_`; тестовый игрок удаляется.

Для ручной проверки Swagger в изменяющих запросах передавай заголовок `x-requested-with` со значением `VolnaApp`. Через сайт он передаётся автоматически. Cookie относится к имени хоста: во время проверки не переключайся между `localhost`, `127.0.0.1` и `0.0.0.0`.

Проверка сохранности данных после замены Pod:

```powershell
python .\scripts\smoke-test.py --keep-state
kubectl rollout restart deployment/accounts deployment/team-info
kubectl delete pod accounts-db-0 team-info-db-0
kubectl rollout status statefulset/accounts-db
kubectl rollout status statefulset/team-info-db
kubectl rollout status deployment/accounts
kubectl rollout status deployment/team-info
python .\scripts\smoke-test.py --verify-persistence
```

Этот сценарий создаёт собственные тестовые записи и проверяет сохранение пользователя, сессии, предпочтения команды, аватарки, игрока и его фото. Он не удаляет PVC и не затрагивает чужие записи.

## Остановка и повторный запуск

```powershell
.\scripts\stop-k8s.ps1
```

Команда завершает только пробросы портов, созданные скриптом проекта. Приложения продолжают работать в кластере. Чтобы временно остановить их, сохранив диски:

```powershell
kubectl scale deployment accounts team-info frontend pgadmin --replicas=0
kubectl scale statefulset accounts-db team-info-db --replicas=0
```

Для возврата к работе выполни `start-k8s.ps1 -SkipBuild`. Не удаляй PVC и не сбрасывай кластер, если нужны данные.

## Данные и переход с Compose

Существующие PVC аккаунтов сохраняются. У Team Info новая отдельная база: начальные сведения о команде создаются автоматически, игроки добавляются через сайт. Старые записи PostgreSQL/MySQL и файлы из Docker-томов не копируются в Kubernetes автоматически. Старый каталог `backend`, SQL и прежние тома оставлены для возможного переноса данных.

`compose.yaml` сохранён для отдельной практики с Docker Compose. Все его сервисы находятся в профиле `compose-lab` и по умолчанию не запускаются. Существующие контейнеры Compose остановлены, их тома сохранены. Основной рабочий сайт использует Kubernetes.

Раньше параллельно работали две копии: Compose с пустым составом и Kubernetes с сохранёнными игроками. Это разные базы, поэтому записи из одной копии не появлялись в другой. Для обычной работы теперь используется только http://localhost:8088. В Compose также указан порт 8088: он не позволит незаметно поднять второй сайт рядом с основным. Включение учебного профиля не переносит в него данные Kubernetes.

Изменения сайта собирай через `scripts/start-k8s.ps1`, как указано выше. Сборка через `docker compose build` сама по себе не обновляет приложения в Kubernetes. `.env.example` остаётся примером настроек Compose; фактический `.env` не изменён.

`healthcheck.test` — команда проверки внутри контейнера. Для API она запускает контейнерный Python и делает запрос к `/ready`, который проверяет также подключение к PostgreSQL. `urllib.request` — встроенный модуль Python; устанавливать его через pip или на компьютер ради этой проверки не нужно. `404` означает, что в запущенной версии приложения нет такого маршрута: проверь исходник и пересобери образ. Фронтенд проверяется встроенной в Alpine командой `wget` по `/healthz`.

## Библиотеки Python

- `pydantic` — проверка и преобразование входных данных.
- `Pillow` — проверка и обработка фотографий и аватарок; импортируется как `PIL`.
- `fastapi` — фреймворк маршрутов и обработчиков HTTP API.
- `uvicorn` — сервер, запускающий приложение FastAPI.
- `psycopg[binary]` — драйвер PostgreSQL с готовыми двоичными компонентами.
- `python-multipart` — разбор HTML-форм и загружаемых файлов.
- `httpx` — HTTP-клиент сервиса Team Info для проверки сессий через Accounts API.

Версии зависимостей закреплены в `requirements.txt` каждого API. Встроенные модули `os`, `contextlib`, `pathlib` и другие отдельно не устанавливаются.

## Файл pyproject.toml

`pyproject.toml` — текстовая конфигурация Python-проекта в формате TOML. В разделе `[project]` указаны название `volleyball-team`, версия `0.1.0` и требование Python `>=3.12`. Версия проекта не обязана совпадать с версией API. Пустой список `dependencies` не означает отсутствия библиотек: для контейнеров они устанавливаются из отдельных `requirements.txt`.

Вызов `FastAPI(...)` создаёт объект приложения в памяти и не создаёт `pyproject.toml`. Настройки инструментов разработки при необходимости располагают в разделах `[tool.*]`. Python 3.12 в Dockerfile соответствует заявленному минимальному требованию проекта.
